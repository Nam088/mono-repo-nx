# @nam088/permission

Permission declaration and NestJS enforcement layer for the mono-repo.

## What this library provides

- Type-safe permission declarations by resource.
- Central registry with expansion (`implies`, `includes`) and lookup helpers.
- Generated `P` refs for IDE autocomplete (`P.user.read` -> `'user:read'`).
- NestJS decorator + guard + module for endpoint-level authorization.

## Core concepts

### 1) Declare permissions

Use `definePermissions(...)` in domain files:

- `implies` for action dependency (example: `update` implies `read`).
- `includes` for group aggregation (example: `manage` includes CRUD actions).

The registry is built in `src/registry.ts` and exported as:

- `PERMISSIONS` runtime registry
- `P` typed refs
- `PermissionKey`, `ResourceName`

### 2) Use typed refs

Use `P.<resource>.<name>` instead of raw strings:

```ts
P.user.read; // "user:read"
P.user.manage; // "user:manage"
```

Refs are generated by:

```bash
npx nx run permission:generate-refs
```

### 3) Protect Nest handlers

Use one decorator with two modes:

```ts
@RequirePermission(P.user.read)                            // single key
@RequirePermission(P.user.read, P.user.update)             // AND mode
@RequirePermission({ any: [P.user.read, P.user.update] })  // OR mode
```

## Nest integration API

### `PermissionModule.forRoot`

Register a resolver using one of:

- class type
- `{ useClass }`
- `{ useExisting }`
- `{ useValue }`
- `{ useFactory, inject }`

### `PermissionGuard`

Guard behavior:

1. Reads metadata from `@RequirePermission`.
2. Requires authenticated `request.user.sub`.
3. Uses resolver in this order:
    - `authorize(...)` if implemented (PDP/remote decision mode)
    - fallback to `resolve(...)` + local `PERMISSIONS.covers(...)`
4. Throws:
    - `UnauthorizedException('unauthenticated')` when user is missing
    - `ForbiddenException('insufficient_permissions')` when denied

### Resolver contract

`PermissionsResolver` supports both styles:

- `resolve(ctx)` -> `string[]` permissions
- `authorize(ctx)` -> final allow/deny boolean

`authorize` is preferred when present. This enables scale-friendly architecture where:

- API is enforcement point (PEP).
- Auth service is decision point (PDP).

## Example module wiring

```ts
import { APP_GUARD } from '@nestjs/core';
import { Module } from '@nestjs/common';
import {
    PermissionGuard,
    PermissionModule,
    REDIS_PERMISSIONS_KEY_BUILDER,
    RedisPermissionsResolver,
} from '@nam088/permission';
import { SharedRedisModule } from '@nam088/redis';

@Module({
    imports: [
        SharedRedisModule.forRoot(),
        PermissionModule.forRoot({
            resolver: RedisPermissionsResolver,
            providers: [
                {
                    provide: REDIS_PERMISSIONS_KEY_BUILDER,
                    useValue: ({ sub }: { sub: string }) => `auth:perms:user:${sub}`,
                },
            ],
        }),
    ],
    providers: [{ provide: APP_GUARD, useClass: PermissionGuard }],
})
export class AppModule {}
```
